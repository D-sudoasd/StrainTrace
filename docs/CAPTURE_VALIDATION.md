# Capture validation and handover

The software is developed on `feat/capture-workbench` from `3853196`. The development contract is `STRAINTRACE_CAPTURE_GOAL.md`. See [Capture workflows](CAPTURE.md) and [upstream source and licenses](CAPTURE_RESEARCH.md).

### Continued TIFF publication across frame-ledger batches

The system-buffered writer keeps up to eight batches of large TIFF descriptors in order, counting the batch being committed. Each batch contains up to 16 frames. SQLite commits remain serial. A failed commit leaves later TIFFs in the frame journal for recovery, with their source identities and trigger associations.

Three interleaved pairs on Windows E: replayed 90 distinct 1,919 × 1,199 Mono16 frames per camera at 90 Hz per camera. Each run paused the first frame-ledger commit by 300 ms. The median run p95 for receipt to TIFF publication fell from 222.1 to 6.5 ms. Receipt to ledger commit moved from 305.2 to 306.0 ms. The median peak queued pixel bytes fell from 201.9 to 17.6 MiB. All 1,080 TIFFs passed decoding and source-pixel checks, and the aggregate TIFF digests matched across variants.

Additional matched runs used the same large replay, a 1,600 × 800 replay at 90 Hz, and 640 × 480 replays in both storage modes without a forced pause. All 4,440 TIFFs across the paused and unpaused runs passed the same checks. In the 1,600 × 800 runs, the previous publication p95 was 4.66 and 4.70 ms. The updated runs measured 16.17 and 4.79 ms. The improvement under a paused ledger commit is reproducible on this replay. Unpaused timings varied.

### Writer notification for markers and final drain

The acquisition thread wakes the writer when it enqueues images or reaches the end of acquisition. A marker also wakes the writer. If there are no more images ready for the current batch, the writer can finish that batch before recording the marker. The marker receipt resolves after its SQLite transaction commits.

On Windows E:, each condition used six paired runs with reversed order on alternating pairs. Each run issued 12 markers in a simulated manual phase. The second condition requested each marker immediately after a 1,024 × 640 Mono16 TIFF was published and while the frame batch was still open.

### GenTL packed image boundaries

PFNC permits packing to continue across rows or restart at each row. Capture uses the GenTL-reported image offset, filled length and padding to select a layout and supplies complete groups to the Harvesters PFNC decoder. It reports ambiguous boundaries when both interpretations fit or when trailing chunk data prevents identifying the image extent. Raw buffers are returned after decode, including on failure. The host receipt timestamp is taken when Harvesters returns the raw buffer. [PFNC boundary rules](https://www.emva.org/wp-content/uploads/GenICam_PFNC_2_4.pdf) · [GenTL buffer metadata](https://www.emva.org/wp-content/uploads/GenICam_GenTL_1_6.pdf)

The installed Harvesters 1.4.3 high-level path gave four exact results in a 30-case probe using known packed arrays. Capture then exercised 20 monochrome and Bayer formats across seven layouts with synthetic GenTL buffers and the same PFNC decoder. All 280 TIFFs matched their source arrays and hashes. The tests covered frame- and row-aligned packing, odd widths, row and frame padding, image offsets, and chunked payloads with explicit row padding. Separate cases verified rejection and buffer return for ambiguous or incomplete input. The delivered pixel format determined the recorded format when the producer reported packed samples despite an unpacked camera setting. Native Viky emulator runs checked raw buffer acquisition and return with its uncompressed formats.
